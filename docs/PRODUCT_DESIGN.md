# 产品设计与实现

## 从信息查询到选择理解

Meridian 围绕三个连续问题组织体验：我还需要完成什么、选择某个事项会改变什么、这个建议有什么依据。路径画布承载要求与选项，侧边面板承载解释和模拟，AI 对话负责补充自然语言理解。

这一分工让结构化规则保留可检查的表达方式，也让自然语言建议有具体的上下文，而不是成为与个人进度脱节的独立聊天入口。

## 结构化学业模型

培养方案按 track、category、requirement 与 option 等实体组织。用户的完成状态单独记录，再与公共要求组合生成工作区。规则关系与目标相关建议分别建模，便于展示同一规则在不同目标下的解释，而不将目标偏好写成规则事实。

相关入口：`src/types/db.ts`、`src/api/trackApi.ts`、`src/hooks/useTrack.ts`、`src/lib/trackUserView.ts`。

## 推荐与可用性

`src/lib/trackRecommendation.ts` 先生成启发式推荐骨架，再请求模型补充理由。返回结构经 Zod 校验，异常时退回骨架。当前增强步骤复用已有节点与连接集合，模型并不提供任意的图重构或全局最优性保证。

这是对可用性和可解释性的取舍：核心结构可以在 AI 请求失败时保留，解释质量仍需结合规则来源核对。

## 无副作用的选择预览

`src/lib/trackSimulation.ts` 使用假设的进度映射计算选项完成后的变化，不直接写库。计算范围是当前要求与分类的学分进度。它不等同于完整先修依赖传播、跨分类推理或未来成绩预测。

## 文档与对话上下文

`src/lib/docExtract.ts` 在浏览器抽取文字 PDF 与文本类文件。`src/lib/personalDocContext.ts` 整理个人资料上下文；服务端 `src/routes/api/ai/chat.ts` 可检索手册片段并代理模型请求。

文件抽取发生在浏览器，并不意味着所有数据只留在浏览器：上传文件和解析记录使用 Supabase，发送给真实 AI 的对话可包含相关文档片段。公开说明必须反映这一数据流。

## 运行边界

前端统一使用 `src/ai/index.ts` 的 provider 接口，mock 与 remote 分别服务于演示和真实调用。服务端验证 Supabase 会话，按用户实施实例内频率限制；多实例下这不是全局共享限流器。

数据访问通过 `src/api/` 封装，界面由 hooks 和 context 消费。数据库与存储访问依赖部署的 RLS 策略，前端访客状态和按钮显隐不构成权限控制。

## 演进方向

可继续验证的方向包括更多学校与年级适配、规则版本管理、完整依赖分析、更系统的模拟测试及分布式请求配额。这些是后续方向，不作为当前已交付能力或效果指标。
